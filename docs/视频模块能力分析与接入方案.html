视频渠道的配置化接入能力
先回答你的三个问题

1. 现在能不能提供视频能力？能，且不用改一行代码。9 个视频渠道已跑通，覆盖 Seedance / Hailuo / Sora / 万相 / Kling / Vidu / Jimeng / Veo，共 30+ 模型。后台建渠道填 key 配价即可。

2. 以后出新大模型能不能快速接？分两种情况。同协议族（比如 Seedance 出 2.5、Hailuo 出新版本）只需在 ModelList 加一行 + 配价，5 分钟。新协议族（新厂商、新请求结构）目前必须写 Go 代码 + 改 9~11 处硬编码，约 300~600 行，1~3 天。

3. 有没有组件化能力？视频链路目前没有——全是硬编码 switch。但仓库里已有成熟的注册表范式（relaykit/relayconvert/text_converter_registry.go）可以照搬。第五节给三级方案，代价从 2 天到 3 周不等。

02架构与请求生命周期

视频是异步任务模型，和 chat 的同步转发是两条完全独立的链路。这点决定了后面所有的改造代价。

两条链路的分野

Chat / Image / Embedding（同步）

注册点：GetAdaptor(apiType)
接口：Adaptor
未知渠道兜底：APITypeOpenAI（common/api_type.go:85）
配置化能力：有 AdvancedCustom(58) 可通过 JSON 配路由

Video / Suno / MJ（异步任务）

注册点：GetTaskAdaptor(platform)
接口：TaskAdaptor（16 方法）+ TaskPollingAdaptor（4 方法）
未知渠道兜底：无，返回 nil → 400
配置化能力：没有 全部硬编码 switch

AdvancedCustom 接不了视频

它是仓库里唯一的配置化接入出路，但只注册在 GetAdaptor（relay/relay_adaptor.go:126），GetTaskAdaptor 的 switch 里没有它。而且它的可配路由白名单只有 8 条（relaykit/dto/channel_settings.go:138-146）：chat / responses / responses-compact / alpha-search / claude-messages / rerank / images / embeddings — 一条视频路径都没有。

03接一个新视频模型要改哪些地方

分两种情况，代价差两个数量级。判断标准只有一个：上游的请求结构和现有某个适配器是否同族。

情况 A：同协议族新模型 5 分钟

比如 Seedance 出 2.5、Hailuo 出新版本、万相出 wan3.0。上游路径和请求结构不变，只是模型名和价格不同。

3setting/ratio_setting/model_ratio.go加默认价（可选，也可让管理员在后台配）

这条路已经是"组件化"的了 — doubao 的 videoPriceTable（task/doubao/constants.go:35）就是数据驱动的价格矩阵，加模型不用碰逻辑。

04现状的 5 个结构性问题

这些是本次调研新发现的，都会直接影响"快速接入"和"给别人用"这两个目标。

1. 视频渠道的 EndpointType 注册被注释掉了 影响下游发现能力

// common/endpoint_type.go:11-18
//case constant.ChannelTypeMidjourney, constant.ChannelTypeMidjourneyPlus:
//	endpointTypes = []constant.EndpointType{constant.EndpointTypeMidjourney}
//case constant.ChannelTypeSunoAPI: ...
//case constant.ChannelTypeKling: ...
//case constant.ChannelTypeJimeng: ...
case constant.ChannelTypeSora:   ← 只有 Sora 是活的
	endpointTypes = []constant.EndpointType{constant.EndpointTypeOpenAIVideo}
default:
	endpointTypes = []constant.EndpointType{constant.EndpointTypeOpenAI}  ← Kling/Vidu/Doubao 落这里

后果：Kling / Jimeng / Vidu / DoubaoVideo / 万相 在 /api/pricing 和 /api/models 里被标成 OpenAI chat 端点。下游拿到模型列表无法区分"这是个视频模型"，只能靠硬编码模型名前缀猜。做转售平台时这条必须先修，否则接入方的第一个问题就是"你们哪些模型是视频的"。

2. 视频模型几乎没有默认价 接入即报错

setting/ratio_setting/model_ratio.go:272 的 defaultModelPrice 里视频模型只有：

sora-2-pro → 0.5

未配价时 ModelPriceHelperPerCall（relay/helper/price.go:200-208）走 GetModelRatio，仍找不到就返回 modelPriceNotConfiguredError，除非用户开了 AcceptUnsetRatioModel。也就是建完渠道直接调用会 400，新人接入的第一个坑。

3. 共享请求结构 TaskSubmitReq 表达力不足 限制新协议接入

// relay/common/relay_info.go:868 — 10 个扁平字段，被 10 个渠道共用
Prompt string; Model string; Mode string; Image string;
Images []string;   ← 无 role 概念
Size string; Duration int; Seconds string; InputReference string;
Metadata map[string]interface{}  ← 所有厂商特有参数的垃圾桶

两个实际后果：

  • Vidu 靠图片数量猜语义（task/vidu/adaptor.go:102）：len(Images)==2 当首尾帧、>2 当参考图。这种猜法在有 6 种 role 的协议上必错。
  • 没有 video / audio 输入字段。参考视频、参考音频这类输入只能塞 Metadata，绕过所有类型校验和计费边界检查 — 而 AGENTS.md 明确警告 Metadata 是计费校验绕过路径。

还有一条硬约束：validatePrompt（relay/common/relay_utils.go:136）要求顶层 prompt 非空。任何把提示词放在嵌套结构里的协议，走共享校验器每个请求都 400。

4. 秒数上限对视频过松 计费安全

MaxTaskDurationSeconds = 3600（relay/common/relay_utils.go:146）。真实视频模型上限普遍是 5~15 秒。这个通用上限只防溢出，不防"用户传 3600 秒把预扣打到天上"。每个新渠道必须在自己的 Validate 里再收紧一次，公共层不会帮你。

5. PerCallBilling 与 ModelPrice 互斥 设计冲突

// controller/relay.go:599
PerCallBilling: common.StringsContains(constant.TaskPricePatches, relayInfo.OriginModelName)
                || relayInfo.PriceData.UsePrice,   ← 配了 ModelPrice 就是 true

// service/task_polling.go:646 — 第 0 条
if bc.PerCallBilling { return }   ← 差额结算被整条短路
这条对"按用量结算"的视频渠道是致命的

凡是希望终态多退少补的渠道（实际出片秒数 ≠ 预估秒数、上游返回真实用量），都不能配 ModelPrice，必须走 ModelRatio（token 维度）。doubao 就是这么做的。而 relay/relay_task.go:203 还有一层：TaskPricePatches 里的模型连 OtherRatios 都不应用。

更麻烦的是 relay.go:599 这一行是所有任务渠道共用的（MJ / suno / kling / vidu / sora / doubao / ali / jimeng / gemini / vertex）。想为某个渠道关掉它，改法要么加渠道级白名单，要么改用 ModelRatio 计费 — 不是一行改动。

05组件化方案（三级）

回答"以后怎么快速接入"。三级方案代价递增、收益递增，可以按顺序做，也可以只做 L1。
好消息：范式不用自己发明

仓库里已有一个成熟的注册表实现可以照搬：relaykit/relayconvert/text_converter_registry.go。它用 TextConverterSpec{ID, From, To, Quality, Req, Resp} 描述一个转换器，builtinTextConverters 数组声明式注册，sync.RWMutex 保护，支持别名和运行时注册。视频适配器完全可以套同一套结构。

风险：低。纯注册层重构，不碰任何业务逻辑和计费。

L2 — 抽公共基类，压缩适配器体积 约 3~5 天

目标：让"必须自写"的 6 个方法降到 2~3 个。现有 9 个适配器平均 350 行，其中大量是同构样板。

抽取物覆盖场景预计省下
taskcommon.BearerAuthBuildRequestHeader 的 Bearer/API-Key 两种范式每渠道 10~15 行
taskcommon.JSONSubmitFlowDoRequest + DoResponse 的"POST JSON → 取 task_id"标准流每渠道 40~60 行
taskcommon.StatusMapper声明式状态映射表替代手写 switch：{"PROCESSING":IN_PROGRESS, ...}每渠道 30~50 行
taskcommon.SecondsResolutionBilling"秒数 × 分辨率档"这个最常见的计费范式（ali/vidu/doubao 三家在用）每渠道 40~80 行
taskcommon.DurationGuard渠道级秒数上限校验 + 计费钳制，修掉第四节第 4 条每渠道 15 行 + 消除一类计费漏洞

收益：新适配器从 300~600 行降到 120~250 行。同族计费范式复用，减少各渠道各写一遍钳制逻辑的漏检风险。
代价：需要重构现有适配器才能验证抽象是否合理（只抽不用等于没抽）。建议先接 2 个新渠道验证范式，再回头重构老的。

L3 — 配置化接入（无需改代码） 约 2~3 周

目标：管理员在后台填 JSON 就能接一个新视频渠道，对标 AdvancedCustom(58) 之于 chat。

L3 能覆盖多少？给个诚实的估计

纯 JSON 模板能覆盖"提交拿 id / 轮询看状态 / 取结果 URL"这个主干，大约是 60~70% 的渠道。覆盖不了的：需要签名算法的（AWS SigV4、火山 HMAC）、需要多步交互的（先传文件再提交）、计费规则是加法或阶梯的、状态机有中间态需要特殊处理的。

所以 L3 不能取代 L1/L2，它是"长尾渠道快速上架"的补充。主力渠道仍然应该写 Go 适配器。

建议：L3 先不做。等 L1+L2 落地、且真的出现"一个月要接 5 个以上新视频渠道"的需求时再评估。过早做配置化会得到一个既不够灵活又难调试的模板引擎。

06转售 / 自产 token 的前置条件

你提到"自产 token 再通过平台中转卖给别人，要别人也能接入"。这件事 new-api 本身就是为此设计的，但视频链路有几个专门的缺口。

视频链路专属缺口 要补

#缺口对接入方的影响优先级
1视频模型的 EndpointType 标错（第四节第 1 条）接入方无法从 /api/models 判断哪些是视频模型，只能问你要文档高
2多数视频模型无默认价你自己上架时每个都要手配，漏配则接入方收到 400高
3无统一的任务列表接口接入方只能逐个 task_id 查，做不了"我的任务列表"页中
4无终态回调（webhook）接入方必须自己轮询，体验差且浪费双方资源中
5无取消任务接口（除个别渠道）误提交的任务无法止损，额度照扣低
6厂商原生协议路由（Kling / Jimeng）暴露了上游身份转售场景下泄露你的上游是谁中
第 4 条：回调机制当前是零实现

我在全仓库搜过 OnVideoTaskTerminal 之类的钩子，0 命中。model/task.go 里刚加的 CallbackURL / CallbackPushedStatus 字段是为 H3 预埋的，但消费它们的代码一行没有。如果要做转售平台，回调应该做进公共层（所有视频渠道共享），而不是某个渠道的私有能力 — 否则每接一个渠道都要重写一遍推送和幂等逻辑。
