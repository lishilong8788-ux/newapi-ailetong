异步任务全链路

视频 / 音乐 / Midjourney 走的那条路。这是最容易出财务事故的地方 —— 请求早就返回了，钱还在后台动。

1为什么需要另一条路

同步和异步的根本差异：钱什么时候结清

💬 同步（对话）

耗时几秒
流程预扣 → 发上游 → 收响应 → 结算 → 返回客户
特点客户拿到响应时，钱已经结清
风险低。算错了当场就能发现

🎬 异步（视频）

耗时几分钟到几十分钟
流程预扣 → 提交上游 → 立刻返回任务 ID
　　　…后台轮询…→ 完成 → 结算
特点客户拿到响应时，钱还冻结着
风险高。结算发生在另一个进程、另一个时刻
核心风险：预扣估少了，你自己兜。
任务已经提交给上游、钱已经花出去了。这时发现客户余额不够 —— 差额只能你承担。
所以异步任务的预扣必须按最坏情况估，并且强制关闭「信任额度旁路」。

2自己动手：走完整条链路

三个按钮 = 三种结局。重点看每一步「钱」怎么动

3三段式计费

为什么不能一次扣完
第一段 · 提交时预扣（按最坏情况估）
客户说「6 秒 2K 视频，带一段参考视频」→ 系统按上限估：6 秒 × 2K 单价 + 参考视频按 15 秒上限估。
余额不够 → 直接拒绝，不提交上游。这是你的成本防线。
第二段 · 提交后微调（可选）
上游返回时说「实际会生成 8 秒」→ 按 8 秒重算，补扣差额。
不是所有渠道都有这一段，取决于上游提交响应里给不给实参。
第三段 · 完成时结算（多退少补）
任务跑完，上游给出真实用量 → 按真实值重算 → 差额补扣或退还。
失败 / 取消 → 全额退还。
一个开关会让第三段失效： 如果这个模型配成了按次固定价格，系统会跳过完成时结算。
逻辑是「既然按次收固定价，实际用了多少秒就无关紧要」。
所以想做「预扣后按实际用量多退少补」的模型，绝对不能配成按次计费 —— 配了的话客户永远按预扣金额付，多退少补完全失效。

4为什么不会重复退款

这是真实存在过的 bug 类型，理解它能帮你验收代码
一个任务失败了要退款。但同时有三个东西可能发现它失败：
① 正常的轮询任务发现了 ② 超时清理任务发现了（任务卡太久） ③ 多机部署时，另一台服务器的轮询也发现了 三个都执行退款 → 退了三次钱
解决办法：更新状态时带上「我认为它现在是什么状态」这个条件。
"把状态从『进行中』改成『失败』" ← 带条件的更新 第一个执行的：条件成立 → 改成功 → 它负责退款 第二三个执行的：条件不成立（已经不是「进行中」了）→ 改失败 → 不退款
数据库层面保证只有一个赢家。
验收要点：任何涉及「钱的状态变更」的新功能， 你都要问开发一句 ——「如果同时有两个进程干这事会怎样？」
答不上来的，大概率有重复扣款/退款的风险。

5轮询配置（客户说进度慢，看这里）

配置项默认值含义 / 什么时候要改
UPDATE_TASK必须 true 总开关。关掉的话任务提交后没人轮询，永远卡在「已提交」
轮询周期15 秒 后台每 15 秒扫一次未完成任务。所以进度最多滞后 15 秒
TASK_TIMEOUT_MINUTES1440（24 小时） 超过就判失败并全额退款。设 0 = 禁用超时清理
TASK_QUERY_LIMIT1000 单轮最多处理多少个任务。任务量大要调高，否则堆积
同渠道任务间隔1 秒 防止把上游查询接口打爆。可在渠道设置里关闭
同渠道 1 秒间隔要注意： 某渠道有 100 个待查任务 → 一轮要走 100 秒，比 15 秒的轮询周期长得多。
任务量大时会自然错峰，这是设计如此。但如果你觉得进度更新太慢， 可以在渠道设置里关掉这个间隔（前提是上游能扛住）。
Gemini / Vertex 有特殊优待：支持实时查询 —— 客户查询时直接去上游拉最新状态，不用等轮询周期。
所以客户会反馈「为什么 veo 的进度更新比别的快」，原因在这。其他渠道只能等后台轮询。

6配置检查清单

视频渠道最容易配错，逐条核对
☐ 渠道类型选对应的视频专用类型（Kling 选 50、Vidu 选 52、Sora 选 55）
　　不能用「OpenAI 兼容」凑 —— 视频走另一套分发逻辑，选错直接失败且报错不说原因
☐ 模型名和系统内置列表逐字一致（大小写敏感）
☐ 定价只填一种：按次填固定价格，按量填倍率，两个别同时填
☐ UPDATE_TASK=true 必须开
☐ 别指望「渠道测试」按钮 —— 视频渠道不支持，提示 not supported 是正常的
☐ 上线前完整走一遍五条路径：提交 / 轮询中 / 成功结算 / 失败退款 / 超时退款
最后一条是验收底线。 只测「提交成功」远远不够 —— 财务事故几乎都出在失败退款和超时退款这两条路径上， 因为它们不常触发，容易漏测。
测法：故意提交一个会失败的任务（比如违规提示词），看钱有没有退回来。

7客户投诉对照表

客户说真实原因怎么处理
「任务一直卡在已提交」UPDATE_TASK 没开，或轮询任务挂了 检查环境变量；看系统任务运行历史
「明明只做了一个视频，扣了两笔」看到的是预扣 + 结算差额两条日志 把两条加起来给他看，总额是对的
「任务失败了钱没退」退款走轮询有延迟；或他看的是预扣那条日志 查日志里有没有「退款」类型的记录
「视频生成好了但链接打不开」多数渠道用上游原始链接，有时效性 让他及时下载；或改走网关代理链接
「为什么按 15 秒收费，我只要 5 秒」带了参考视频，预扣按 15 秒上限估 解释终态会退差额；让他等结算完再看
🎯 如果只记三件事
1. 预扣按最坏情况估，终态多退少补 —— 所以客户会看到两条日志，总额才是实际
2. 配成按次固定价格会跳过终态结算，多退少补失效
3. 必测失败退款和超时退款 —— 财务事故都出在这两条不常触发的路径上
