双钱包机制图解

用户额度 vs 令牌额度。和分组是正交的两套机制 —— 分组管「走哪条路、什么价」，钱包管「能花多少钱」。

1一句话理解

不是两个钱包各出一半，是同一笔钱被记两次账
一次消费同时从两个地方扣同样的金额：用户钱包（真钱）+ 令牌额度（这把钥匙的消费上限）。
令牌额度是「限额器」，不是「余额」 —— 它不代表钱，只代表「这把钥匙最多还能花多少」。
类比：公司给你一张公司信用卡（用户钱包，真钱在这）， 同时给这张卡设了每张副卡的消费上限（令牌额度）。
你刷 100 元 → 公司账上少 100，副卡的可用上限也少 100。 不是花了 200。

2两个钱包的关键差异

这张表是本页最重要的内容 —— 两者规则不对称，这是设计有意为之

💰 用户额度（钱包）

存在「用户」上 · 代表真实的钱
软限制 · 允许透支成负数
余额不足时不中断请求，欠费记为负余额。
理由：保证日志记的扣费额和余额变动始终对得上账， 不会出现「日志说扣了但余额没动」的对账黑洞。
充值、兑换码、邀请奖励都进这里

🔑 令牌额度（限额器）

存在每把「令牌」上 · 不代表钱
硬限制 · 严格拦截
不够就直接拒绝请求，返回 403。
用的是原子预留（检查+扣减一步完成）， 所以并发请求不可能同时通过检查后超扣。
可勾选「无限额度」跳过检查
这个不对称必须记住： 真正能拦住失控消费的是令牌额度，不是用户余额。
用户余额是允许透支的 —— 如果你以为「余额扣到 0 就自动停」， 那是错的，它会继续跑成负数。
要硬性封顶，必须给令牌设额度。

3自己动手：调数字看会发生什么

重点试「令牌不够」和「钱包不够」两种，看它们的结果完全不同

4扣款顺序：为什么先扣令牌

顺序不是随意的，反了会出财务问题
① 先扣令牌额度 ── 硬检查，不够就 403，此时还没碰用户的钱 ② 再扣用户钱包 ── 软扣减，允许负数 如果 ② 失败（数据库错误）： → 自动回滚 ①，把令牌额度加回去 → 不会出现「令牌扣了但钱没扣」的错账
为什么先扣令牌？因为令牌是硬拦截。先做会失败的那一步， 失败了就干净退出，不用回滚。如果反过来先扣钱再检查令牌， 每次令牌不足都要回滚一次真金白银的扣款 —— 回滚越多，出错概率越大。
预扣费也走这套。请求发出前先按「最坏情况」冻结一笔， 用完后按真实用量结算，多退少补。所以你在日志里会看到 「预扣费后补扣费」或「退还」的记录，这是正常的。

5一个重要例外：信任额度旁路

老客户余额充足时，系统会跳过预扣直接放行
余额远超本次预估花费时，系统不做预扣，直接发请求，用完再一次性结算。
好处：省掉一次数据库写，高并发下明显降低压力。
但异步任务强制关闭这个优化。 因为视频/音乐任务返回后还在后台烧钱几分钟，必须提前锁死全额， 否则客户余额只剩 5 元也能提交一个要花 50 元的任务， 钱已经花在上游了，差额只能你自己承担。

6后台在哪配

三个位置
1. 改用户钱包余额
用户 → 编辑某用户 → 剩余额度
或让用户自己充值 / 用兑换码。支持批量操作
2. 改令牌额度
令牌 → 编辑 → 额度　｜　勾选「设为无限额度」
客户自己也能在 个人面板 → API 令牌 里设（不能超过自己余额）
3. 查实际扣了多少
日志 → 消费日志（可按用户/令牌/模型筛选）
日志里同时记录预扣额、实际额、各项倍率。这是唯一可信的对账依据

7客户常见投诉对照表

大部分「扣费异常」的工单都在这张表里
客户说真实原因怎么答
「我还有余额，为什么报额度不足？」 令牌额度用完了，不是钱包。两者是独立的两个数 让他看令牌那一栏的额度，或改成无限额度
「余额怎么变成负数了？」 正常行为。钱包是软限制允许透支，用来保证对账一致 解释这是设计如此；要硬性封顶请给令牌设额度
「明明只调了一次，怎么扣了两笔？」 看到的是预扣 + 结算差额两条记录，实际总额是对的 把两条加起来给他看
「充了钱怎么还是不能用？」 钱进了用户钱包，但令牌额度没跟着涨 令牌额度需要单独调高，或设为无限
「任务失败了钱没退？」 异步任务退款走轮询，有延迟；或已退但他看的是预扣那条日志 查日志里有没有「退款」类型的记录
第一条和第四条是最高频的。 根因都是客户（和很多运维）把「令牌额度」当成了「余额的一部分」。
记住这个说法就够了：钱包是钱，令牌额度是刷卡上限。上限不够，钱再多也刷不出去。

三种典型配置
场景用户钱包令牌额度效果
个人客户
最常见		 充多少是多少无限额度 简单，钱包一个数说明一切
企业多项目 公司总预算，如 10000 元 每项目一把令牌

🎯 如果只记三件事
1. 同一笔钱扣两个地方，不是花两倍
2. 令牌额度是硬拦截，用户余额允许透支成负数 —— 要封顶就设令牌额度
3. 先扣令牌再扣钱包，钱包失败会自动回滚令牌
