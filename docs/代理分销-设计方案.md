# 代理分销 — 设计方案

> 状态：P0+P1+P2 已实现（2026-09-08）；上线前需在系统设置中显式开启 AgentEnabled
> 关联代码：`model/user.go`、`model/topup.go`、发票管理模块（作为审核流模板）
> 实现说明：

>   PostgreSQL 会连坐回滚客户充值，此为对原设计的必要修正
> - 退款反冲行使用 `topup:reversed` 后缀 source_type 避开唯一索引冲突（设计 5.5 的修正）
> - 金额列用 float 而非 decimal 类型（`model/agent.go`）——glebarez SQLite 迁移器无法

>   走 shopspring/decimal
> 最后更新：2026-09-08

## 1. 背景与目标

平台需要一套完整的代理商（分销）体系：代理商拿到专属推广链接与二维码，分享获客；客户充值后代理商按比例获得佣金；代理商能看到名下客户的充值、余额、用量明细，能查看收益构成，能提现并追溯提现记录。平台侧需要审核代理商主体资质、审核提现、调整分佣比例，并能评估每个代理商的推广效果。

目标拆成三个视角，各自独立入口，互不混用：

| 视角 | 入口 | 使用者 | 核心诉求 |
|---|---|---|---|
| 代理商工作台 | `/agent` | 代理商本人 | 拿链接、看客户、看收益、提现 |
| 代理商管理 | `/agent-management` | 平台运营 / 财务 | 审主体、审提现、调比例、查流水 |
| 分销效果分析 | `/agent-analytics` | 平台运营 / 管理层 | 横向对比代理商产出、追踪转化 |

关于第三个页面是否必要：**必要**。前两个页面回答的是"这个代理商的钱对不对"，回答不了"哪个代理商值得加大投入、哪个渠道在空转"。缺了它，运营只能靠导出 Excel 手工比对，代理商规模一过二十家就失控。但它是纯读页面，不参与资金，所以排在 P2，不阻塞前两个。

### 2.2 差距

原生 aff 是"注册送额度"，不是代理分销。两者的根本差别：aff 的奖励在注册那一刻就结清了，客户后续充多少、用多少与上级再无关系。代理分销要的是随客户流水持续产生佣金，且佣金能出金。

逐项缺口：

1. **无持续分佣** — 只有注册时一次性固定赠额，与客户后续充值无关。
2. **无客户明细** — 拿不到名下客户的充值额、剩余额度、用量。
3. **无提现** — `aff_transfer` 只能转成自己的平台余额，没有出金，没有提现记录。
4. **无代理商主体** — 无个人/企业身份、无资质审核、无"资料未审核不得提现"的门禁。
5. **无二维码**、无独立页面、无 admin 审核台、无效果分析。
6. **无佣金账本** — `aff_quota` 是一个 int 汇总值，无法追溯每一笔佣金来自哪个客户的哪张订单，对账和纠纷处理没有依据。

### 2.3 可复用的现成模式

**发票管理模块是提现审核流的直接模板。** 它已经把"用户提交 → 平台审核 → 通过/驳回 → 状态机 → 用户端与 admin 端双页面"这条路走通了，且踩过的坑都已修好：

- 提交时快照主体信息，后续改资料不影响已提交单据（`model/invoice.go:90` 注释）；
- 前端目录结构 `web/src/features/invoice-management/`：`api.ts` / `types.ts` / `constants.ts` / `components/*-columns.tsx` / `*-table.tsx` / `*-dialogs.tsx` / `*-provider.tsx` / `lib/format.ts`。

## 3. 已确认的产品决策

| 决策项 | 结论 | 影响 |
|---|---|---|
| 计佣基数 | 按充值金额分成 | 挂钩点只在充值结算，不碰 relay 计费链路 |
| 提现出口 | 转平台余额 + 银行打款，用户自选 | 需要银行信息存储与财务打款流程 |
| 分佣层级 | 只做一级 | 不需要关系表，复用 `users.inviter_id`；无环路问题 |

## 4. 数据模型

三张新表。一级分销不需要独立关系表，绑定关系直接用 `users.inviter_id`（已有 index）。

### 4.1 为什么不复用 `aff_quota`

`aff_quota` 是单个 int 汇总值，quota 单位。佣金必须独立建账本，理由有三条：

1. **可追溯** — 每笔佣金要能回答"来自哪个客户、哪张充值单、当时什么比例"。汇总值答不了，一旦代理商质疑金额就无从对账。
2. **可反冲** — 客户退款要写负向流水，汇总值只能做减法，减完就丢失了历史。
3. **单位不同** — 佣金是人民币金额（decimal），`aff_quota` 是 quota（int）。混用会在汇率/赠送比例上出现精度和语义错误。

`aff_quota` 与原有的注册赠额机制**保持原样不动**，两套并存：`aff_quota` 继续管"注册送额度"，`agent_commission` 管"充值分佣"。不迁移、不改语义，避免影响存量用户数据。

### 4.2 `agent_profile` — 代理商主体

```go
type AgentProfile struct {
    Id     int `json:"id"`
    UserId int `json:"user_id" gorm:"uniqueIndex"`

    // 身份与状态
    AgentType string `json:"agent_type" gorm:"type:varchar(16);not null;default:'personal'"` // personal | company
    Status    string `json:"status" gorm:"type:varchar(16);not null;default:'incomplete';index"`
    Level     string `json:"level" gorm:"type:varchar(32);default:''"`  // 运营自定义等级标签，仅展示

    // 分佣比例：0.0000 ~ 1.0000，空值时取全局默认
    CommissionRate *float64 `json:"commission_rate" gorm:"type:decimal(6,4)"`

    // 主体信息（个人）
    SubjectName string `json:"subject_name" gorm:"type:varchar(64);default:''"`
    IdNo        string `json:"id_no" gorm:"type:varchar(64);default:''"`

    // 主体信息（企业）
    CompanyName string `json:"company_name" gorm:"type:varchar(255);default:''"`
    TaxNo       string `json:"tax_no" gorm:"type:varchar(64);default:''"`

    // 收款信息
    BankName    string `json:"bank_name" gorm:"type:varchar(255);default:''"`
    BankAccount string `json:"bank_account" gorm:"type:varchar(64);default:''"`
    BankBranch  string `json:"bank_branch" gorm:"type:varchar(255);default:''"`

    // 联系方式
    ContactName  string `json:"contact_name" gorm:"type:varchar(64);default:''"`
    ContactPhone string `json:"contact_phone" gorm:"type:varchar(32);default:''"`
    ContactEmail string `json:"contact_email" gorm:"type:varchar(128);default:''"`

    // 审核
    AuditBy      int    `json:"audit_by" gorm:"default:0"`
    AuditTime    int64  `json:"audit_time" gorm:"default:0"`
    RejectReason string `json:"reject_reason" gorm:"type:varchar(255);default:''"`
    ApprovedAt   int64  `json:"approved_at" gorm:"default:0"` // 首次审核通过时间，通过后永不清零；计佣以此为准

    Remark    string `json:"remark" gorm:"type:varchar(255);default:''"` // 运营备注，不对代理商展示
    CreatedAt int64  `json:"created_at" gorm:"autoCreateTime"`
    UpdatedAt int64  `json:"updated_at" gorm:"autoUpdateTime"`
}
```

`CommissionRate` 用 `*float64` 而非 `float64`：区分"未单独设置，跟随全局默认"与"显式设为 0，不给佣金"。这是 AGENTS.md 里可选标量必须用指针的规则在业务语义上的体现。

状态机：

```
（无 profile） --用户提交申请--> pending(待审核) --通过--> active(已生效)
                                    |                      |
                                    +--驳回--> rejected(驳回) --重新提交--> pending
                                                           |
incomplete(运营指定，资料待补充) --提交--> pending             |
                                                           |
active --运营停用--> suspended(已停用)  // 停止产生新佣金，已有佣金仍可提现
active --代理修改资料--> pending(重审中)  // 仍然计佣，见下
```

`ApprovedAt`（`approved_at`）字段记录"首次审核通过的时间"，通过后**永不清零**。它是计佣的唯一开关，而不是当前 `status`：

- **没有 profile / `incomplete` / `pending` / `rejected`**：看不到推广链接（响应里不返回 `aff_code`、`promo_link`、`register_link`），也**不产生佣金**。未审核通过的人不会被平台顺手发一个推广码。
- **`approved_at > 0`**：计佣。已通过审核的代理修改银行卡等资料会回到 `pending` 重审，此时**仍然计佣** —— 运营复核一张改过的银行卡期间断佣，和 bug 无法区分。
- **`suspended`**：停止产生新佣金，但已有佣金仍在账本里、仍可提现。推广链接保留（已印在物料上的码不能撤，否则已邀请客户的归因会断）。
- **只有 `active` 才能提现。**

`incomplete` 现在只可能来自运营后台指定（`AdminCreateAgentProfile`）：运营先把某个用户定为代理商、资料随后补全。用户自己走的路径是"无 profile → 提交申请 → pending"，不再经过 `incomplete`。

> **变更说明（对原设计的有意收紧）**：本文档早期版本规定 `incomplete` 状态下即可拿链接推广并产生佣金，目的是降低启动门槛。实际运行后改为"先申请 → 运营审核通过 → 才开通推广链接、才入佣金"。
>
> 直接原因是一个 bug：`GET /api/agent/profile` 曾调用 `EnsureAgentProfile`，任何用户点开「推荐计划」页就会插入一行 `status=incomplete`。叠加上"`incomplete` 也能计佣"的口径，等于点一下页面就成了能拿佣金的代理，后台代理商列表也退化成"所有点过这个页面的注册用户"。现在读接口不再建行，并在启动时做两步数据整理：`BackfillAgentApprovedAt()` 给历史已通过的代理回填 `approved_at`（取 `audit_time`，缺失则退回 `updated_at`），再 `PruneEmptyAgentProfiles()` 清理那些由访问页面产生的零信息行（仅当所有主体/收款/联系/备注字段皆空、无运营审核痕迹、且该用户在佣金和提现表里都没有任何记录时才删）。两步都是 best-effort，失败只记日志，不阻断网关启动。

### 4.3 `agent_commission` — 佣金流水（账本）

只增不改的账本表。任何金额调整都通过新增反向记录实现，不 UPDATE 历史行。

```go
type AgentCommission struct {
    Id          int `json:"id"`
    AgentUserId int `json:"agent_user_id" gorm:"index;index:idx_agent_comm_status,priority:1"`
    FromUserId  int `json:"from_user_id" gorm:"index"` // 产生佣金的下级客户

    // 来源：唯一索引三元组，幂等的最终防线
    SourceType string `json:"source_type" gorm:"type:varchar(32);not null;uniqueIndex:idx_agent_comm_source,priority:2"`
    SourceId   int    `json:"source_id" gorm:"not null;uniqueIndex:idx_agent_comm_source,priority:3"`

    // 金额（人民币）
    BaseAmount float64 `json:"base_amount" gorm:"type:decimal(18,4);not null"` // 计佣基数 = 实付金额
    Rate       float64 `json:"rate" gorm:"type:decimal(6,4);not null"`         // 当时生效的比例（快照）
    Amount     float64 `json:"amount" gorm:"type:decimal(18,4);not null"`      // 佣金金额

    Status        string `json:"status" gorm:"type:varchar(16);not null;index:idx_agent_comm_status,priority:2"`
    AvailableTime int64  `json:"available_time" gorm:"default:0;index"` // 冻结期结束时间
    WithdrawalId  int    `json:"withdrawal_id" gorm:"default:0;index"`  // 被哪张提现单占用

    Remark     string `json:"remark" gorm:"type:varchar(255);default:''"`
    CreateTime int64  `json:"create_time" gorm:"autoCreateTime;index"`
}
```

唯一索引 `idx_agent_comm_source` 覆盖 `(agent_user_id, source_type, source_id)`，`priority:1` 在 `AgentUserId` 上。**这个索引是幂等的唯一依据** —— 支付回调重放在生产环境是常态而非异常，不能靠"先查后插"判重（并发下必漏）。插入冲突时视为已处理，静默跳过。

`Rate` 存快照而不是运行时读 `agent_profile`：运营调比例后，历史佣金必须保持原样，否则对账时金额会漂移。

状态机：

```
pending(冻结中) --冻结期满--> settled(可提现) --发起提现--> frozen(提现占用)
                                                              |
    +--提现驳回/失败--> settled                                  |
    |                                                         +--打款完成--> paid(已结清)
    +-- 客户退款 --> 新增一条 reversed 负向记录（不改原行）
```

### 4.4 `agent_withdrawal` — 提现单

```go
type AgentWithdrawal struct {
    Id          int `json:"id"`
    AgentUserId int `json:"agent_user_id" gorm:"index;index:idx_agent_wd_status,priority:1"`

    Amount       float64 `json:"amount" gorm:"type:decimal(18,4);not null"`     // 申请金额
    Fee          float64 `json:"fee" gorm:"type:decimal(18,4);default:0"`      // 手续费
    ActualAmount float64 `json:"actual_amount" gorm:"type:decimal(18,4);not null"` // 实际到手

    Method string `json:"method" gorm:"type:varchar(16);not null"` // balance | bank
    Status string `json:"status" gorm:"type:varchar(16);not null;index:idx_agent_wd_status,priority:2"`

    // 提交时的主体信息快照（JSON），后续改资料不影响已提交单据
    ProfileSnapshot string `json:"profile_snapshot" gorm:"type:text"`

    // 审核与打款
    AuditBy      int    `json:"audit_by" gorm:"default:0"`
    AuditTime    int64  `json:"audit_time" gorm:"default:0"`
    PayTime      int64  `json:"pay_time" gorm:"default:0"`
    PayVoucher   string `json:"pay_voucher" gorm:"type:varchar(255);default:''"` // 打款凭证/流水号
    RejectReason string `json:"reject_reason" gorm:"type:varchar(255);default:''"`
    Remark       string `json:"remark" gorm:"type:varchar(255);default:''"`

    CreateTime int64 `json:"create_time" gorm:"autoCreateTime;index"`
}
```

状态机按出口分两条路：

```
method=balance（转平台余额，免审核）
  提交 --> paid(已完成)          // 同一事务内完成，秒到

method=bank（银行打款，需审核）
  提交 --> pending(待审核)
            |--通过--> approved(待打款) --财务打款--> paid(已打款)
            |                              |
            |                              +--打款失败--> rejected（佣金解冻回 settled）
            +--驳回--> rejected（佣金解冻回 settled）
```

`balance` 免审核的依据：钱没有离开平台，只是从佣金账本转到用户 quota 余额，风险等同于运营手工加额度，且 `creditTopUpQuota` 已有 int32 上限保护。`bank` 是真实出金，必须人工过一道。

### 4.5 `users` 表冗余汇总列

为列表排序与首屏统计加三列，避免每次都对账本做聚合：

```go
AgentCommissionTotal     float64 // 累计佣金（含冻结）
AgentCommissionAvailable float64 // 可提现
AgentWithdrawnTotal      float64 // 已提现
```

**这三列只用于展示与排序。任何资金判定（能否提现、可提金额）必须回 `agent_commission` 表用行锁实时计算。** 冗余列允许短暂不一致，资金判定不允许。

### 4.6 数据库兼容

三库（SQLite / MySQL ≥5.7.8 / PostgreSQL ≥9.6）必须同时可用：

- 全部用 GORM 方法建表与查询，不写原生 SQL；
- 字段名避开 `group` / `key` 等保留字（本设计已避开）；
- 迁移只用 `ALTER TABLE ... ADD COLUMN`，不用 `ALTER COLUMN`；
- 不加 `gorm:"default:true"` 类布尔默认值（MySQL/PG 归一化不同会导致 AutoMigrate 反复 ALTER），默认值在构造与请求归一化里给；
- 行锁统一走 `lockForUpdate(tx)`，禁止 GORM v1 的 `tx.Set("gorm:query_option", "FOR UPDATE")`（v2 会静默忽略，锁根本没加上）。

## 5. 分佣引擎

### 5.1 计佣公式

```
base   = topUp.Money            // 实付人民币金额
rate   = agent_profile.CommissionRate ?? AgentDefaultRate
amount = decimal(base) * decimal(rate)   // 保留 2 位小数，向下取整
```

**基数必须取 `topUp.Money`（实付金额），不能取充值到账的 quota。** 充值常配赠送比例（`common/topup-ratio.go`），用 quota 做基数会把平台赠送的部分也分给代理商，等于平台替代理商的佣金买单两次。

金额计算全程走 `shopspring/decimal`，不用 float 乘法。`decimal` 已是项目依赖（`model/topup.go` 在用）。向下取整而非四舍五入：宁可少给 1 分，不可多给 —— 多给的累积起来是平台净损失且无法追回。

### 5.2 挂钩点

充值结算共六条路径，全部要覆盖：

| 路径 | 位置 |
|---|---|
| 易支付 | `model/topup.go:176` `RechargeEpay` |
| Stripe | `model/topup.go:235` `Recharge` |
| 管理员手工完成 | `model/topup.go:449` `ManualCompleteTopUp` |
| Creem | `controller/topup_creem.go` 对应结算函数 |
| Waffo | `controller/topup_waffo.go` |
| Waffo Pancake | `controller/topup_waffo_pancake.go` |

订阅订单（`model/subscription.go`）是否计佣，见 §12 待确认项。

### 5.3 写入策略

**在充值成功的原事务内插入一条 `agent_commission`（status=`pending`），不动任何余额、不加任何行锁。**

这个选择的三条理由：

1. **幂等天然成立** — 唯一索引兜底，回调重放时插入冲突直接跳过，比事务外补偿可靠得多。事务外补偿需要额外的重试队列和对账任务，是纯粹的复杂度增加。
2. **不引入锁竞争** — 只是一条 INSERT，不 UPDATE 代理商行，避免"同一代理商名下多个客户同时充值"时互相阻塞。这是高并发下最容易被忽略的坑：如果在事务内 UPDATE `users.agent_commission_total`，热门代理商会成为写热点。
3. **失败不影响充值** — 分佣写入失败绝不能让客户充值回滚。客户付了钱必须到账，佣金可以后补。

因此冗余汇总列的更新**放在事务外**，失败只记日志不影响主流程，由日终对账任务修正。

```go
// 伪代码，置于充值事务内、creditTopUpQuota 之后
if err := recordAgentCommissionTx(tx, topUp); err != nil {
    if !errors.Is(err, ErrAgentCommissionDuplicate) {
        // 仅记录，不中断充值
        common.SysError("agent commission record failed: " + err.Error())
    }
}
```

注意这里**吞掉错误**：分佣是附加价值，充值是主业务，主业务不能被附加价值拖垮。但重复错误要单独识别并静默（那是正常的回调重放），其他错误必须落日志以便排查。

### 5.4 冻结期

新佣金落库时 `status=pending`、`available_time = now + AgentFreezeDays*86400`（默认 7 天）。后台任务定期把到期的 `pending` 改成 `settled`。

这道闸门是防"充值 → 立即提现 → 申请退款"套利的**唯一屏障**，不能省。冻结天数应当覆盖支付渠道的退款窗口。

任务挂在现有的定时任务框架下（参考 `model/system_task.go` 的调度方式），频率一小时一次即可 —— 冻结期以天计，不需要分钟级精度。

### 5.5 退款反冲

客户退款时必须写一条 `status=reversed` 的负向记录（`amount` 为负），**不物理删除原记录**。原因是原记录可能已被提现占用甚至已打款，删掉会让账本对不上。

三种情形分别处理：

| 原佣金状态 | 处理 |
|---|---|
| `pending` / `settled` | 写负向记录，可提现余额自然减少 |
| `frozen`（提现审核中） | 写负向记录并标记该提现单需人工复核 |
| `paid`（已打款） | 写负向记录，可提现余额变为负数，挂账抵扣后续佣金 |

允许可提现余额为负是有意设计：这是代理商对平台的欠款，用后续佣金自动抵扣。提现校验时用 `可提现 >= 申请额` 判断，负余额自然无法提现。

## 6. 提现流程

### 6.1 提交时的硬门禁

按顺序校验，任一不过即拒：

1. `agent_profile.status == active`（资料已审核通过）；
2. `method == bank` 时，`bank_name` / `bank_account` / 主体名称非空；
3. `amount >= AgentMinWithdrawal`（默认 100 元）；
4. 该代理商无 `pending` 或 `approved` 状态的在途提现单（同时只允许一笔在飞）；
5. `amount <= 实时可提现余额`，余额在事务内用 `lockForUpdate(tx)` 计算。

第 5 条是资金安全的核心。**可提现余额必须由账本聚合得出，绝不能用"累计佣金 - 已提现"的减法。** 减法在并发下会超提：两个请求同时读到相同的旧值，各自通过校验，最终提走两倍金额。

正确做法：事务内锁定该代理商 `status=settled` 的佣金行，聚合求和，通过后把这些行改为 `frozen` 并写入 `withdrawal_id`。占用与校验在同一事务，不可能超提。

```go
// 伪代码
tx := DB.Begin()
rows := lockForUpdate(tx).Where("agent_user_id = ? AND status = ?", uid, StatusSettled).Find(&commissions)
available := sum(rows.Amount)
if available < req.Amount { return ErrInsufficientCommission }
// 按时间顺序占用，先产生的先提（FIFO）
picked := pickUntil(rows, req.Amount)
tx.Model(...).Where("id IN ?", picked.Ids).Updates(map[string]any{
    "status": StatusFrozen, "withdrawal_id": wd.Id,
})
```

FIFO 占用（先产生的佣金先提）而非任意挑选：让账本的占用顺序可预测，对账和纠纷排查时能复现。

### 6.2 余额出口

`method=balance` 在同一事务内完成，复用 `creditTopUpQuota`：

```
佣金金额（元） × common.QuotaPerUnit = 到账 quota
```

转换必须走 `common.QuotaFromDecimalChecked`，捕获饱和并按 AGENTS.md 要求把 clamp 标记落到日志。虽然单笔提现远不会碰到 int32 上限，但这是防御性下限 —— 一旦上游数据异常，宁可失败并告警，不可静默截断。

余额出口的佣金状态直接从 `settled` → `paid`，跳过 `frozen`，因为不存在审核等待期。

### 6.3 银行出口

`method=bank` 提交后进 `pending` 队列，占用的佣金转 `frozen`。

- **审核通过** → `approved`，佣金保持 `frozen`，进入财务打款队列；
- **审核驳回** → `rejected`，佣金解冻回 `settled`，写驳回原因；
- **财务标记打款完成** → `paid`，佣金转 `paid`，回填 `pay_voucher`；
- **打款失败** → `rejected`，佣金解冻回 `settled`。

打款是纯人工线下动作，系统只记录状态与凭证号，不对接银行接口。这是有意的：对接银行代付需要企业资质、风控审查和额外合规成本，收益远不及一个"标记完成"按钮。

## 7. 推广链接与归因

### 7.1 链接形态

沿用现有 `?aff=` 参数体系，不新建。注册链路已经在解析（`controller/user.go:263`、`controller/oauth.go:367`）。

```
完整链接：https://{host}/register?aff={aff_code}
短链：    https://{host}/r/{aff_code}    → 302 到上面
```

短链只需一个匿名路由做重定向，顺便把 `aff_code` 写入 Cookie。截图里用的是短链形式（`https://tokease.cn/r/2dfZb4`），观感上更适合线下分享和二维码。

### 7.2 归因规则

- 落地时把 `aff_code` 写入 Cookie，有效期 30 天；
- 注册时优先取 URL 参数，其次取 Cookie；
- 绑定关系写入 `users.inviter_id` 后**永久不可变更**。

不可变更是运营纪律而非技术限制：允许改上级会立刻产生"抢客户"的纠纷，且历史佣金归属会变得无法解释。如需调整，走人工数据修正并留审计记录。

自我推荐防护：`inviter_id != user.Id`。一级分销不存在环路，无需递归检测。

### 7.3 二维码

**前端生成，不做后端接口。** 用 `qrcode` npm 包画到 canvas，下载走 `canvas.toDataURL()`。

省一个接口、省服务端 CPU、省一次网络往返。二维码内容就是短链字符串，没有任何需要服务端保密或校验的成分，放后端纯属多余。

## 11. 分销效果分析页 `/agent-analytics`

纯读页面，不参与资金流转。目的是回答运营的三个问题：**哪个代理商值得加投？哪个在空转？带来的客户质量如何？**

### 11.1 为什么需要单独一页

前两个页面是事务页面 —— 处理单据、审核状态。它们能告诉你"张三这个月佣金 5000 元"，但回答不了：

- 张三带来的 30 个客户里，有几个是充过钱的真实用户，几个是注册就沉睡的水号？
- 李四佣金只有 800，但他的客户平均充值额是张三的三倍，谁更值得培养？
- 上个月新增的 12 个代理商，有几个已经出单？

这些是决策数据，混进事务页面会让两边都难用。按运营分层的原则，事务与分析分开入口。

### 11.2 全局概览卡

| 指标 | 计算方式 |
|---|---|
| 代理商总数 / 活跃数 | `agent_profile` 按状态计数；活跃 = 近 30 天有新佣金 |
| 推广客户总数 | `users` 按 `inviter_id != 0` 计数 |
| 付费客户数 / 付费率 | 有过成功充值的客户数 / 推广客户总数 |
| 推广贡献流水 | `agent_commission.base_amount` 求和 |
| 累计佣金支出 | `agent_commission.amount` 求和（扣除 `reversed`）|
| 实际佣金率 | 佣金支出 / 推广流水 |
| 待付佣金 | `settled` + `frozen` 求和 |

"实际佣金率"是最重要的一个数：它反映真实成本，会因为不同代理商的比例差异而偏离名义默认值。这个数持续走高说明高比例代理商占比在上升，需要复盘定价策略。

### 11.3 图表

复用 `web/src/features/dashboard/` 的图表组件（基于 recharts）。

1. **推广趋势** — 双轴折线：新增客户数 + 推广流水，按日/周/月切换；
2. **代理商排行** — 横向柱状：按推广流水 / 佣金 / 客户数 / 付费率排序，Top 20；
3. **佣金支出趋势** — 面积图：按月展示佣金支出与流水，叠加实际佣金率折线；
4. **客户质量分布** — 散点图：横轴客户数、纵轴客均充值，每个点是一个代理商。右上角是优质代理商，右下角是"拉人头但不产出"。

第 4 张图是这一页的核心价值。它能一眼区分"量大质差"与"量小质优"两类代理商，这个判断用表格是看不出来的。

### 11.4 代理商明细表

每行一个代理商，列为：代理商、客户数、付费客户数、付费率、推广流水、客均充值、佣金、实际佣金率、首次出单时间、最近出单时间、30 天活跃度。

支持全部列排序与 CSV 导出。

"最近出单时间"用于识别沉睡代理商：超过 60 天无新佣金的应当进入运营回访名单。

### 11.5 数据来源与性能

聚合查询的数据量会随时间线性增长，必须控制：

- 概览卡与趋势图走**按日预聚合表**，不实时扫全表。参考 `model/usedata.go` 现有的按日统计模式；
- 明细表按代理商聚合，代理商数量级在百级，可以实时算；
- 客户质量散点图的数据量等于代理商数，同上；
- 所有聚合加时间窗口上限（默认近 12 个月），不允许无界查询。

预聚合表 `agent_daily_stat`（P2 阶段引入）：

```go
type AgentDailyStat struct {
    Id          int
    AgentUserId int     `gorm:"uniqueIndex:idx_agent_daily,priority:1"`
    StatDate    string  `gorm:"type:varchar(10);uniqueIndex:idx_agent_daily,priority:2"` // YYYY-MM-DD
    NewCustomers int
    PayCustomers int
    TopupAmount  float64 `gorm:"type:decimal(18,4)"`
    Commission   float64 `gorm:"type:decimal(18,4)"`
}
```

日期用 `varchar(10)` 而非 date 类型：三库的 date 处理差异（尤其 SQLite 无原生 date）会带来不必要的兼容成本，字符串比较对 `YYYY-MM-DD` 格式完全够用且天然可排序。

## 12. 系统配置项

新增配置走现有 `model/option.go` + `controller/option.go` 的模式，在系统设置里加一个"代理分销"分组。

| 配置键 | 默认值 | 说明 |
|---|---|---|
| `AgentEnabled` | `false` | 总开关，关闭时隐藏所有入口且不产生佣金 |
| `AgentDefaultRate` | `0.05` | 默认分佣比例（5%）|
| `AgentMaxRate` | `0.30` | 比例上限，运营调整时的硬约束 |
| `AgentFreezeDays` | `7` | 佣金冻结天数 |
| `AgentMinWithdrawal` | `100` | 最低提现金额（元）|
| `AgentWithdrawalFeeRate` | `0` | 提现手续费比例 |
| `AgentAutoApprove` | `false` | 主体审核是否自动通过 |
| `AgentBalanceNeedAudit` | `false` | 余额出口是否也需要审核 |
| `AgentSubscriptionCommission` | `false` | 订阅订单是否计佣（见 §14）|

`AgentMaxRate` 存在的意义：防止运营误操作把比例设成 `1.5` 导致平台每笔充值倒亏。比例校验在服务端做，不能只靠前端表单。

配置项在 `controller/option.go` 里需要加数值范围校验分支（参考现有 `QuotaForInviter` 的处理，`controller/option.go:145`）。

## 13. 安全与合规红线

### 13.1 资金安全

1. **幂等靠唯一索引，不靠代码判重。** 支付回调重放是常态。
2. **可提现余额靠账本聚合 + 行锁，不靠减法。** 减法必然超提。
3. **佣金比例服务端校验上限**，`0 <= rate <= AgentMaxRate`。
4. **金额全程 decimal**，佣金向下取整；转 quota 用 `common.QuotaFromDecimalChecked` 并按 AGENTS.md 要求记录 clamp。
5. **退款写负向记录，不物理删。** 允许余额为负作为挂账。
6. **同时只允许一笔在途提现单**，避免并发提现绕过余额校验。
7. **冻结期不可省**，是套利的唯一屏障。

### 13.2 隐私边界

代理商可见：下级用户名、显示名、用户 ID、注册时间、充值总额、剩余额度、累计用量、账号状态。

代理商**不可见**：邮箱、手机号、API Key、请求内容与日志明细、其他代理商的任何数据。

接口层面必须在 SQL 的 `Select` 里显式限定字段，不能查出完整 User 再靠序列化过滤 —— 那样一次字段增加就可能意外泄露。

### 13.3 银行信息处理

`model/invoice_profile.go:16` 已有明文存储 `bank_name` / `bank_account` 的先例，`common/` 下也不存在 AES 工具。

本设计**沿用既有先例**（不在此功能里新造加密层），但收紧读取面：

- 代理商本人查看自己的账号：脱敏，只保留后 4 位；
- admin 列表页：脱敏；
- admin 提现详情页：完整展示（财务打款必需）；
- 导出文件：脱敏，完整账号不进 CSV。

这是既存技术债，本功能不扩大也不顺手重构。如需系统性加密，应当作为独立事项覆盖发票与代理两个模块。

### 13.4 权限

- `/api/agent/*` 走 `middleware.UserAuth()`，所有查询强制按 `agent_user_id = 当前用户` 过滤，禁止用请求参数指定他人 ID；
- `/api/agent/admin/*` 走 `middleware.AdminAuth()`；
- 审核、比例调整、人工调整佣金、标记打款四个动作写审计日志（参考 `controller/audit.go`），记录操作人、时间、变更前后值、原因。

审计日志不是可选项。涉及资金的人工操作若无留痕，出现纠纷时无法界定责任。

## 14. 待确认项

以下四点会影响实现，需要在开工前定：

1. **订阅订单是否计佣？** 订阅（`model/subscription.go`）是另一条付费路径。若计佣，续费是否每期都给？建议：首期计佣，续费不计（避免长期被动成本），用 `AgentSubscriptionCommission` 开关控制。
2. **兑换码充值是否计佣？** 兑换码（`model/redemption.go`）没有实付金额，无法确定计佣基数。建议不计佣。
3. **提现手续费由谁承担？** 默认 `AgentWithdrawalFeeRate=0`（平台承担）。若要代理商承担，需在提现弹窗明确展示扣费明细。
4. **代理商准入方式？** 是所有用户默认都是代理商（拿到链接就能推广），还是需要申请审批后才开通？建议默认开放（降低门槛，符合现有 aff 的语义），资质只在提现前要求。

## 16. 测试要点

按 AGENTS.md 的后端测试规范，用 `testify/require` + `assert`，确定性表驱动测试。要覆盖的是真实不变量，不是覆盖率：

| 测试 | 保护的不变量 |
|---|---|
| 计佣金额精度 | 各种金额与比例组合下佣金精确、向下取整、不出现浮点误差 |
| 幂等 | 同一 `(agent, source_type, source_id)` 重复写入只成功一次 |
| 比例上限 | 超过 `AgentMaxRate` 的比例被拒绝 |
| 可提现余额 | 并发提现不超提；负余额无法提现 |
| 提现占用与解冻 | 驳回后佣金精确回到 `settled`，金额不丢不多 |
| 退款反冲 | 各状态下反冲后余额正确，历史记录不被删除 |
| 隐私字段 | 客户列表接口不返回邮箱/手机号 |
| 越权 | 代理商无法查询他人数据；非 admin 无法访问 admin 接口 |
| quota 转换饱和 | 异常大额转余额时失败并记录 clamp，不静默截断 |

前端测试（vitest）：金额格式化、状态映射、表单校验边界。注意 jsdom 下 Base UI 菜单会崩，表格测试的 fixture 要避开会挂载行操作下拉的状态。
